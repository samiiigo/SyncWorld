# Mobile alarms, push, and the Expo toolchain for SyncWorld (as of Nov 14, 2026)

Context: SyncWorld is on Expo SDK 54 (RN 0.81, expo-router), uses expo-notifications local notifications on native and FCM web push on web. Goal: every member's device rings at one agreed moment, even if the app is closed or the phone is locked or silenced.

## iOS: AlarmKit (iOS 26+) and fallbacks on older iOS

### Takeaway
AlarmKit (iOS 26+) is the only App Store-legal way for a third-party app to ring a real, full-screen alarm that breaks through silent mode and Focus. It needs a usage string, a per-app opt-in from the user, and native Swift code. In Expo that means a community module or a custom Expo module plus a dev build, never Expo Go. On iOS < 26, the most you can do is a local notification: sound capped at 30 s, no silent-switch bypass unless Apple grants the Critical Alerts entitlement (rarely given), and at most 64 pending requests.

### Cited Findings
- Apple WWDC25 session 230, "Wake up to the AlarmKit API": "When it fires, the alert breaks through the silent mode and the current focus." The alert shows the custom title and the app name, with Stop and optional Snooze. — [WWDC25 230](https://developer.apple.com/videos/play/wwdc2025/230/)
- Alarms appear on the Lock Screen, in the Dynamic Island and StandBy, and on a paired Apple Watch. — [WWDC25 230](https://developer.apple.com/videos/play/wwdc2025/230/)
- Users opt in per app: "People opt in to enable alarm functionality for each app on their device." The app adds `NSAlarmKitUsageDescription` to Info.plist and calls `AlarmManager.shared.requestAuthorization()`, or the system prompts on the first schedule. Apps should check `AlarmManager.shared.authorizationState` (.notDetermined / .authorized / .denied) and tell the user in the UI when an alarm will not be scheduled. — [WWDC25 230](https://developer.apple.com/videos/play/wwdc2025/230/)
- Schedule types: **Fixed**, "a single future date… This schedule is absolute and does not change when device timezone changes" (`Alarm.Schedule.fixed(date)`); and **Relative**, a time of day with optional weekly recurrence that follows time-zone changes. — [WWDC25 230](https://developer.apple.com/videos/play/wwdc2025/230/)
- Countdown: "If your alarm supports countdown functionality, your app is required to implement it using a Live Activity", added to the app's widget extension using `ActivityConfiguration` with `AlarmAttributes<Metadata>`. The system shows its own countdown when the Live Activity can't be shown, for example after a restart before first unlock. — [WWDC25 230](https://developer.apple.com/videos/play/wwdc2025/230/)
- Buttons can run your own code through App Intents (custom stop or secondary intent; for example a `LiveActivityIntent` with `openAppWhenRun = true`). — [WWDC25 230](https://developer.apple.com/videos/play/wwdc2025/230/)
- Custom sound: `AlertConfiguration.AlertSound.named("Chime")`. The file must be in the main bundle or in Library/Sounds; without one, the default system sound plays. AlarmKit presents alarms through ActivityKit. — [WWDC25 230](https://developer.apple.com/videos/play/wwdc2025/230/)
- Apple's positioning: alarms are for countdowns and scheduled alerts such as wake-up alarms, and "are not a replacement for other prominent notifications, like critical alerts or time-sensitive notifications." — [WWDC25 230](https://developer.apple.com/videos/play/wwdc2025/230/)
- Without authorization, alarms fail to schedule silently. — [Tessl AlarmKit skill summary (secondary)](https://tessl.io/registry/dpearson2699/swift-ios-skills/files/skills/alarmkit/SKILL.md)
- Localizing `NSAlarmKitUsageDescription` in InfoPlist.xcstrings had a bug that was fixed in iOS 26.1 beta 2. — [Apple Dev Forums thread 802749](https://developer.apple.com/forums/thread/802749)
- Community RN/Expo wrappers for AlarmKit. None is official Expo, all need a native build, none work in Expo Go:
  - `expo-alarm-kit` (v0.1.6, iOS 26+, Expo SDK 50+, needs App Group and prebuild, low downloads at about 472) — [pkgstats](https://www.pkgstats.com/pkg:expo-alarm-kit)
  - `react-native-ios-alarmkit` (Nitro module, v0.7.5, no-op on Android and on iOS < 26, works with Expo and bare RN) — [README on unpkg](https://unpkg.com/react-native-ios-alarmkit@0.7.5/README.md)
  - `react-native-nitro-ios-alarm-kit` (no-op on Android, limited simulator support) — [GitHub](https://github.com/Gautham495/react-native-nitro-ios-alarm-kit)
  - `react-native-alarm-scheduler` (Expo Modules API: Android exact alarms plus iOS AlarmKit, needs a dev build) — [pkgstats](https://www.pkgstats.com/pkg:react-native-alarm-scheduler)
  - Others: `@raphckrman/react-native-alarm-kit` (README says still under development), `@zulfio/react-native-alarm-kit`, `rn-native-alarmkit`, `expo-alarm-module` — [pkgstats raphckrman](https://www.pkgstats.com/pkg:@raphckrman/react-native-alarm-kit), [npm expo-alarm-module](https://npmjs.com/package/expo-alarm-module)
- iOS < 26, notification sound length: an Apple engineer stated a single notification sound cannot exceed 30 seconds. Custom sounds longer than that fall back to the default sound. — [Notifee iOS behaviour docs](https://docs.page/invertase/notifee/react-native/ios/behaviour); [Apple Dev Forums 783705](https://developer.apple.com/forums/thread/783705)
- iOS pending local notification limit: an Apple engineer confirmed a limit of 64 simultaneous pending requests per app, with no workaround. One report says scheduling more than 64 can stop anything from firing. — [Apple Dev Forums 811171](https://developer.apple.com/forums/thread/811171); [flutter_local_notifications #2312](https://www.github.com/MaikuB/flutter_local_notifications/issues/2312)
- Critical Alerts need a special entitlement that Apple grants through a request form and limits to a narrow set of purposes. Rejections are reported ("Because Critical Alerts are disruptive, they are meant to be used for a very restricted number of purposes" — anecdotal). — [Apple Dev Forums 773648](https://developer.apple.com/forums/thread/773648); [Apple Dev Forums 794822](https://developer.apple.com/forums/thread/794822); [Reddit r/iOSProgramming (anecdotal)](https://redlib.hyperreal.coffee/r/iOSProgramming/comments/1h7x53c/apple_wont_allow_proper_3rd_party_alarm_apps)
- Time-sensitive notifications (`interruptionLevel = .timeSensitive`, entitlement `com.apple.developer.usernotifications.time-sensitive`) break through Focus and Scheduled Summary but do not override the silent switch. Critical alerts do bypass the silent switch. LOW CONFIDENCE: the Apple doc page fetched empty, and this description came from the fetch tool's general knowledge, not page text. — [Apple docs: timeSensitive](https://developer.apple.com/documentation/usernotifications/unnotificationinterruptionlevel/timesensitive)

### Inferences
- A social or group app like SyncWorld is a plausible fit for AlarmKit's "scheduled alert" use (Fixed schedule at the voted UTC instant). Apple's framing centers on alarms and timers, though, so App Review might question non-alarm-clock use. Keep the alarm user-initiated and explicit (the user opts in to "ring me at the moment").
- Use `Alarm.Schedule.fixed(Date)` for the agreed instant. It is absolute, so time-zone changes don't move it, which is what SyncWorld wants.
- Recommended iOS plan: AlarmKit on iOS 26+ (behind a capability check). Fall back to an expo-notifications local notification marked time-sensitive with a sound under 30 s on iOS < 26. Keep total pending notifications under 64 (only upcoming SyncWorld moments, not reminder spam).
- A countdown in the Dynamic Island requires a widget extension. Expo needs a config plugin or a module that adds the extension (for example via `@bacons/apple-targets`, not verified here) or one of the modules above.
- SDK 56 raised the minimum iOS to 16.4 (see the Expo section), so the fallback path still covers iOS 16.4 to 25.x.

## Android: exact alarms, full-screen intents, Doze/OEMs, reboot, and Expo libraries

### Takeaway
To ring at an exact moment on Android you need an exact alarm, ideally `setAlarmClock()`, which "the system never adjusts" and which exits low-power modes. You also need a full-screen-intent notification on a high-importance channel. Play allows `USE_EXACT_ALARM` (auto-granted, non-revocable) and pre-granted `USE_FULL_SCREEN_INTENT` (Android 14+) only for apps whose core functionality is alarms, timers, calendars, or calls. SyncWorld will likely have to use `SCHEDULE_EXACT_ALARM`, which the user grants and is denied by default on Android 14+ fresh installs, and ask the user for FSI access. Alarms are cleared on reboot and must be rescheduled from BOOT_COMPLETED.

### Cited Findings
- Exact alarm methods, from least to most critical: `setExact()` ("as long as other battery-saving measures aren't in effect"), `setExactAndAllowWhileIdle()` ("even if battery-saving measures are in effect"), and `setAlarmClock()`: "Because these alarms are highly visible to users, the system never adjusts their delivery time. The system identifies these alarms as the most critical ones and leaves low-power modes if necessary to deliver the alarms." — [Android: Schedule alarms](https://developer.android.com/training/scheduling/alarms)
- Apps targeting Android 12+ must declare one of the "Alarms & reminders" permissions, or a `SecurityException` occurs. Apps targeting 13+ may declare either `SCHEDULE_EXACT_ALARM` or `USE_EXACT_ALARM`. — [Android: Schedule alarms](https://developer.android.com/training/scheduling/alarms)
- `USE_EXACT_ALARM`: "Granted automatically; Cannot be revoked by the user; Subject to an upcoming Google Play policy; Limited use cases." `SCHEDULE_EXACT_ALARM`: "Granted by the user; Broader set of use cases; Apps should confirm that the permission has not been revoked." — [Android: Schedule alarms](https://developer.android.com/training/scheduling/alarms)
- `SCHEDULE_EXACT_ALARM` "is not pre-granted to fresh installs of apps targeting Android 13 (API level 33) and higher". Backup-and-restore to Android 14 denies it. Existing grants carry over on upgrade to 14. — [Android: Schedule alarms](https://developer.android.com/training/scheduling/alarms); [Android 14 behavior change: exact alarms denied by default](https://developer.android.com/about/versions/14/changes/schedule-exact-alarms)
- Check `canScheduleExactAlarms()`. If the permission is revoked, "your app stops, and all future exact alarms are canceled". On grant the system sends `ACTION_SCHEDULE_EXACT_ALARM_PERMISSION_STATE_CHANGED`, and the app should reschedule as it does on BOOT_COMPLETED. Send users to settings with `Settings.ACTION_REQUEST_SCHEDULE_EXACT_ALARM`. — [Android: Schedule alarms](https://developer.android.com/training/scheduling/alarms)
- "Android considers exact alarms to be critical, time-sensitive interruptions. For this reason, exact alarms aren't affected by foreground service launch restrictions." — [Android: Schedule alarms](https://developer.android.com/training/scheduling/alarms)
- Reboot: "By default, all alarms are canceled when a device shuts down." Apps use `RECEIVE_BOOT_COMPLETED` plus a receiver, which "only works if the app has already been launched by the user at least once." — [Android: Schedule alarms](https://developer.android.com/training/scheduling/alarms)
- Doze: ordinary alarms "don't fire when the device is in Doze mode… deferred until the device exits Doze". Use an exact alarm. — [Android: Schedule alarms](https://developer.android.com/training/scheduling/alarms)
- Play policy on Exact Alarm: `USE_EXACT_ALARM` is restricted, and "apps must only declare this permission if their core functionality supports the need for an exact alarm" (examples: alarm or timer apps, calendar apps with event notifications). Other apps should "evaluate if using SCHEDULE_EXACT_ALARM as an alternative is an option". Don't use it for "non-critical features that do not directly contribute to the app's main purpose". Declare in Play Console. — [Play Console Help: Permissions and APIs policy (answer 9888170)](https://support.google.com/googleplay/android-developer/answer/9888170); background in the [July 27, 2022 policy announcement](https://support.google.com/googleplay/android-developer/answer/14554661)
- Play policy on Full Screen Intent: on Android 14+ it is auto-granted only to apps whose core functionality involves setting an alarm or receiving phone or video calls. Others "will not be automatically granted this permission" and must request it from the user. Apps targeting 14+ submit a Play Console declaration "to establish pre-grant eligibility". — [Play Console Help (answer 9888170)](https://support.google.com/googleplay/android-developer/answer/9888170)
- AOSP FSI behavior: on Android 14+ Play revokes the permission for apps without calling or alarm features. Check `NotificationManager#canUseFullScreenIntent()` and send the user to `ACTION_MANAGE_APP_USE_FULL_SCREEN_INTENT`. Without FSI, the notification shows as a heads-up for 60 seconds (locked: first in list; screen off: AOD shows it) instead of a full-screen launch. — [AOSP: FSI limits](https://source.android.com/docs/core/permissions/fsi-limits)
- An upcoming Play deadline (2027-01-27) for "Understanding foreground service and full-screen intent requirements" (removes geofencing as an approved FGS use case). — [Play policy deadlines page](https://support.google.com/googleplay/android-developer/answer/12253906)
- OEM killers: Xiaomi (MIUI/HyperOS) and Samsung rank among the worst on the dontkillmyapp scorecard. Xiaomi adds autostart and its own battery saver on top of standard Android, and the standard battery-optimization exemption does not stop OEM killers. Samsung promised in 07/2024 to drop non-standard optimizations; whether that shipped is unverified. — [dontkillmyapp Samsung](https://dontkillmyapp.com/samsung?app=Truple); [react-native-background-guardian OEM docs](https://www.mintlify.com/ivangonzalezg/react-native-background-guardian/resources/oem-compatibility); [ProAndroidDev: Beyond Doze](https://proandroiddev.com/beyond-doze-building-reliable-background-execution-on-modern-android-including-oem-realities-5fa0a6e05672)
- Play restricts `REQUEST_IGNORE_BATTERY_OPTIMIZATIONS` to specific app categories. The usual workaround is to open `ACTION_IGNORE_BATTERY_OPTIMIZATION_SETTINGS`, which needs no permission. Secondary sources only. — [react-native-background-guardian battery docs](https://www.mintlify.com/ivangonzalezg/react-native-background-guardian/concepts/battery-optimization)
- Notifee: Invertase archived the repo on April 7, 2026 (last release v9.1.8, Dec 2024) and points users to expo-notifications or the community fork `react-native-notify-kit`, a drop-in that is New-Architecture-only and not usable in Expo Go (v10.4.3 at the time). — [DEV: Notifee is archived (fork author)](https://dev.to/marco_crupi/notifee-is-archived-heres-a-maintained-new-architecture-drop-in-replacement-3ib5); [react-native-notify-kit docs](https://docs.page/marcocrupi/react-native-notify-kit); [notify-kit background restrictions](https://docs.page/marcocrupi/react-native-notify-kit/react-native/android/background-restrictions)
- Expo-module option covering both platforms: `react-native-alarm-scheduler` (Android exact alarms + iOS AlarmKit; dev build required). — [pkgstats](https://www.pkgstats.com/pkg:react-native-alarm-scheduler)

### Inferences
- SyncWorld's core purpose ("everyone rings at the agreed moment") arguably *is* an alarm feature, so a `USE_EXACT_ALARM` / FSI declaration might be accepted. The safer default is still `SCHEDULE_EXACT_ALARM` with an in-app explainer, a `canScheduleExactAlarms()` check, and a fallback to `setExactAndAllowWhileIdle` or a high-priority notification. Declaring `USE_EXACT_ALARM` without qualifying risks Play rejection.
- Implementation: schedule with `setAlarmClock()` (RTC wall-clock UTC ms of the voted instant). On fire, post a notification on a high-importance channel with an alarm-usage audio attribute and a full-screen intent to a ringing Activity. Persist scheduled moments locally and reschedule from BOOT_COMPLETED, the permission-state-changed broadcast, TIME_SET/TIMEZONE_CHANGED (not sourced here), and every app launch or push receipt.
- expo-notifications' date trigger alone doesn't guarantee `setAlarmClock` semantics or full-screen ringing. A custom Expo module (Kotlin, about 200 lines plus a config plugin for manifest receivers and permissions) or `react-native-alarm-scheduler` / `react-native-notify-kit` is the realistic route. All need a dev build.
- Onboarding should deep-link users to the Alarms & reminders, Full-screen notifications, and battery optimization settings, plus OEM-specific autostart guidance (dontkillmyapp).

## Push: APNs/FCM, Expo Push Service, reliability, and clock sync

### Takeaway
Remote push is best-effort and should only carry the schedule ("moment X at UTC T"), never act as the alarm itself. Each device then schedules a local alarm (AlarmKit, setAlarmClock, or a local notification) well ahead of time and re-syncs on every app open or push. Expo Push is free, best-effort, at-least-once, capped at 600 notifications/s per project. Direct FCM/APNs is supported too.

### Cited Findings
- Expo: "Expo makes the best effort to deliver notifications to the push notification services operated by Google and Apple"; "a notification may be delivered to Google or Apple more than once or not at all, although these cases are rare." Final delivery depends on Apple's and Google's policies. — [Expo push FAQ](https://docs.expo.dev/push-notifications/faq/)
- Rate limit: "600 notifications per second per project". Excess requests fail, so throttle and retry (expo-server-sdk-node does this). — [Expo push FAQ](https://docs.expo.dev/push-notifications/faq/)
- Receipts only show whether Apple or Google *received* the message (ticket id → receipt). They do not confirm device display. — [Expo push FAQ](https://docs.expo.dev/push-notifications/faq/)
- Cost: "There is no cost associated with sending notifications through Expo push notification service." — [Expo push FAQ](https://docs.expo.dev/push-notifications/faq/)
- Priority `high` "gives your notification the greatest likelihood that Android will display the notification". Intermittent Android delivery issues often trace to priority. — [Expo push FAQ](https://docs.expo.dev/push-notifications/faq/)
- Direct FCM/APNs: "You can use any push notification service for Expo projects". `getDevicePushTokenAsync` returns native tokens. — [Expo push FAQ](https://docs.expo.dev/push-notifications/faq/)
- SDK 55: using push notifications in Expo Go on Android now throws an error, and the app.json `notification` field was removed (prebuild throws if present). — [Expo SDK 55 changelog](https://expo.dev/changelog/sdk-55)
- Apple forums discuss limits on consecutive pushes, including critical alerts. — [Apple Dev Forums 802539](https://developer.apple.com/forums/thread/802539)

### Inferences
- Architecture: (1) the server finalizes the vote → stores `moment_utc_ms`; (2) sends a data or visible push with the moment id, plus Realtime or DB sync when the app is open; (3) the client schedules the local alarm immediately and re-checks on foreground, on silent push, and on boot; (4) a second "reminder" push about 1 h before acts as a backstop; (5) server-side tracking of "scheduled ack" per device lets the group UI show who is armed.
- Clock skew: local alarms fire on device wall clock, which is normally NTP/carrier-synced, so skew is usually small. For in-app countdown display, compute a server offset (`offset = serverTime - (t_send + rtt/2)`) and render the countdown from `Date.now() + offset`. OS alarm APIs only accept device time, so store the alarm in absolute UTC. Don't "correct" the scheduled time by the offset unless the offset is large, which would mean the user changed their clock manually.
- Expo Push is fine for schedule delivery. A precise ring can't depend on the push arriving on time (Android Doze or OEM killers, iOS throttling, background-push limits).

### Gaps
- No authoritative source fetched on APNs/FCM delivery latency or throttling of background (content-available) pushes, or on server time-offset algorithms. The clock-skew guidance above is engineering inference.

### Takeaway
SDK 58 (RN 0.88, released about Oct 21, 2026) is current. SyncWorld is four SDKs behind. Expo Go's store builds have become unreliable for anything but the newest or App-Store-approved SDK: SDK 55/56 never reached the stores, and the new Expo Go will support only SDK 58. ## Web and desktop: what browsers can do for alarms

### Takeaway
Browsers can't schedule a wake-up alarm. Web push needs a server to send it at the moment (best-effort timing). There is no API to ring through silent or Do Not Disturb or to show full-screen when the browser or tab is closed. On iOS, web push works only for Home Screen web apps (iOS 16.4+). Treat web as "notification plus in-tab ring while open", not a reliable alarm.

### Cited Findings
- iOS web push arrived with iOS 16.4 for web apps added to the Home Screen. Permission can't be requested from a regular Safari tab. It needs HTTPS, a web manifest, and a service worker. — [MagicBell: PWA iOS limitations](https://www.magicbell.com/blog/pwa-ios-limitations-safari-support-complete-guide); [Ionic blog (Feb 2023)](https://ionic.io/blog/?p=4945); [firt.dev iOS PWA notes](https://firt.dev/notes/pwa-ios/)
- Declarative Web Push (no service worker required) shipped for Home Screen web apps in iOS/iPadOS 18.4 (Mar 2025) and in macOS Safari 18.5, including regular Safari tabs with notification permission. — [WebKit: Meet Declarative Web Push](https://webkit.org/?p=16535); [Progressier demo](https://progressier.com/pwa-capabilities/declarative-web-push)
- EU (OLDER INFO, 2024): Apple first removed Home Screen web apps in EU iOS 17.4 betas under the DMA, then reversed on Mar 1, 2024.
